## Goal

Wire the provider lifecycle methods (`init`, `dispose`) into core, and ship the 0.2.0 release. The async `createContext` migration and CLI/Web callsite updates were absorbed into T-022 to avoid a two-API limbo, so this task focuses on what remains: lifecycle + release.

## Acceptance Criteria

- [ ] `createContext` calls `provider.init?.()` once at startup (after instantiation, before returning the context)
- [ ] CLI commands and `runWeb` call `provider.dispose?.()` on shutdown / cleanup paths
- [ ] TUI unmount / Ink exit also runs `provider.dispose?.()`
- [ ] Web's `runWeb` `close()` already awaits the watcher unsubscribe; extend it to also await `ctx.provider.dispose?.()`
- [ ] All existing tests still pass
- [ ] Version bumps: all three workspace packages from `0.1.x` to `0.2.0`
- [ ] CHANGELOG entry (or changeset markdown) documents the breaking signature change (`createContext` is now `Promise<StoreContext>`) and the new `provider:` config key

## Notes

`init` matters for remote providers (Jira / Linear) that need to validate auth or fetch a status mapping at startup — the file provider's `init()` is a no-op `mkdir` and was already deferred in T-021 to avoid an eager I/O on every CLI invocation. With lifecycle wired here, providers can opt in by implementing the optional methods.

`dispose` is the symmetrical cleanup: chokidar watchers, HTTP keep-alive sockets, GraphQL subscriptions. The file provider already tracks watchers in a `Set<FSWatcher>` for this exact purpose.

Don't ship Phase 2 (Jira) before this lands — without `init/dispose` wired, a Jira provider can't validate auth before the first network call and can't shut down cleanly.
