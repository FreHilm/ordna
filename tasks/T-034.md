## Goal

Explore a fourth storage backend that fills a gap none of `file` / `hybrid` / `namespace` covers: **agent-readable task files + clean working tree on `main` + full per-task git history**.

The model: tasks live as `tasks/*.md` files on a dedicated orphan branch (default name `ordna`). Ordna materialises that branch through a `git worktree` (e.g., at `.ordna/worktree/`) on launch, then operates on files within the worktree. The user's normal working tree is unaffected — `git status` on `main` shows nothing task-related, but `git log refs/heads/ordna -- tasks/T-001.md` works, `git blame` works, PRs against the `ordna` branch review task edits like any other diff.

This task is an **exploration / decision task**, not a build commitment. The outcome is either (a) a green light to implement, (b) a decision to fold the missing capabilities into `namespace` instead (commit-history variant + on-demand export), or (c) closed as not worth the maintenance tail.

## Acceptance Criteria

### Decision

- [ ] A written recommendation in this task's Notes section: **build / fold-into-namespace / skip**, with the reasoning.
- [ ] Identify at least one concrete user profile this mode would serve that the existing three modes don't (and isn't comfortably served by the alternatives in §Alternatives below).
- [ ] Estimate the implementation + ongoing maintenance cost honestly (rough LOC, new code paths in auto-detect, CI test matrix expansion, docs surface).

### Design (only required if recommendation is "build")

- [ ] Worktree location decided: `.ordna/worktree/` in repo root (gitignored), `$XDG_CACHE_HOME/ordna/<repo-hash>/`, or other — with rationale.
- [ ] Worktree lifecycle: how `init()` detects vs creates vs attaches; how to recover when the user deletes / corrupts the worktree dir; how two Ordna processes (TUI + web) share it safely.
- [ ] Commit cadence: auto-commit per write vs batched. If auto-commit, document the deliberate break from Ordna's "commits are explicit" principle. If batched, design where the staging area lives given the worktree is rarely visited.
- [ ] Sync model: orphan branch never merges with `main`; pulls use `--ff-only` (with rebase fallback?) so the ordna branch stays linear. Standard `git push ordna` for outbound.
- [ ] Auto-detection signal: how does Ordna recognise a branch-mode repo on first run? `refs/heads/ordna` exists OR `.ordna/worktree/` exists OR config flag. Slot into `auto-detect.ts`'s priority order (probably before namespace, after file).
- [ ] Migration path from / to other modes. At minimum: documented manual steps; ideally an `ordna migrate --to=branch` command.

### Alternatives evaluated

- [ ] **Namespace + commit history.** Change `refs/ordna/tasks/<id>` to point at commits (one task = one commit chain) instead of blobs. Each commit's tree carries just that one task file. Gives `git log` per task without a worktree. Trade-off: heavier storage (commit + tree per version), no file-tools access.
- [ ] **`ordna export tasks/`.** Snapshot the current task state into a directory on demand for agent runs. Cheap to implement, ergonomic for agents, but no real-time sync — every agent invocation runs export first.
- [ ] **Status quo (close this task).** Document the trade-off explicitly in the README's storage modes table so users self-select among the existing three.

### Tests (only required if recommendation is "build")

- [ ] Worktree-lifecycle tests: fresh repo creates orphan branch + worktree; second launch attaches; deleted-worktree recovers; concurrent TUI+web don't race.
- [ ] Auto-detect tests: branch-mode repo signals are recognised before file mode triggers.
- [ ] Sync tests: two clones of the same `ordna` branch can each commit + push + pull without conflicts on non-overlapping tasks; overlapping edits surface as merge conflicts the user resolves manually (standard git semantics — no auto-renumber needed here because the branch is one timeline).
- [ ] Cross-mode round-trip: a repo migrated `file → branch → file` doesn't lose data.

## Notes

### Why this gap exists

Today's coverage matrix:

| | Agents can `cat` files | Clean working tree on main | Per-task `git log` / `blame` |
|---|---|---|---|
| `file`      | yes | no  | yes |
| `hybrid`    | yes | no  | yes |
| `namespace` | no  | yes | no  |
| **branch (proposed)** | yes (in worktree) | yes | yes |

Branch mode is the only one where all three hold simultaneously.

### Costs that won't show up until you ship

- **Worktree management is the work.** Each launch needs to detect-or-create the worktree, handle deletion, handle the user manually switching the worktree's branch, handle two Ordna processes sharing it.
- **Auto-commit vs. "commits are explicit".** Ordna's principle says commits never run on the user's behalf. This mode either breaks that (auto-commits on the ordna branch) or makes the user manually commit in a worktree they rarely visit.
- **Loss of "branches as boards" property.** Like namespace, task edits become global rather than per-feature-branch. PRs reviewing feature branches won't include task-edit diffs alongside the code — those happen on the ordna branch separately.
- **First-launch latency.** `git worktree add` is ~100–500ms. Subsequent launches free.
- **Auto-detect priority logic gets a fourth branch.** Each new mode adds a row to the decision tree and a column to the docs table; the cognitive load on "what mode is this repo?" grows.

### Sketch (for reference if we build)

```
$REPO/
├── src/                       # code, on main / feature branches
├── .git/                      # one git dir, shared
├── .ordna/
│   ├── config.yaml            # storage: branch
│   └── worktree/              # ← `git worktree add --orphan -b ordna .ordna/worktree`
│       └── tasks/
│           ├── T-001.md
│           └── T-002.md
└── .gitignore                 # contains `.ordna/worktree/`
```

`BranchBackend.create(task)` becomes roughly: write `<worktree>/tasks/T-NNN.md`, `git -C <worktree> add tasks/T-NNN.md && git -C <worktree> commit -m "create T-NNN"`, push debounced to origin.
