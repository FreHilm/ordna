## Goal

Make the first-run experience zero-friction across the three storage modes. When a project has no `.ordna/config.yaml`, Ordna inspects the directory for storage signals (existing files / existing refs) and either auto-configures itself or — when the signals are absent but the project is a git repo — asks the user which mode they want via the TUI or web UI.

The result: opening an Ordna board in any project Just Works. Existing file-mode projects keep behaving as today. Hybrid- and namespace-mode projects (e.g., from a teammate who cloned a repo using one of those modes) get auto-detected and configured without manual setup.

## Acceptance Criteria

### Detection module

- [x] `packages/core/src/storage/auto-detect.ts` exports `detectStorageMode(cwd: string): Promise<DetectedMode>`:
  ```ts
  type DetectedMode =
    | { mode: "file" | "hybrid" | "namespace"; reason: string }  // confident — auto-configure
    | { mode: "ask"; reason: string }                            // git repo, no signals — prompt user
    | { mode: "default-file"; reason: string };                   // no git, no signals — silently default to file
  ```
- [x] Detection order:
  1. `refs/ordna/tasks/*` refs exist → `namespace`
  2. `refs/ordna/state` ref exists → `hybrid`
  3. `tasks/*.md` files exist → `file`
  4. cwd is a git repo (and none of the above) → `ask`
  5. else (no git, nothing else) → `default-file`
- [x] Edge cases:
  - If both file artifacts AND namespace refs exist (shouldn't happen normally) — namespace wins (refs are the explicit signal; files might be stale)
  - If both hybrid sync ref AND namespace task refs exist — namespace wins
- [x] Detection is read-only — no files written, no refs created. The caller decides what to do with the result.

### Config loading

- [x] `loadConfig` (in `packages/core/src/config.ts`) gains the following behavior: if `.ordna/config.yaml` is missing, call `detectStorageMode(cwd)`. Outcomes:
  - `{ mode: "file" | "hybrid" | "namespace" }` (auto-detected) → load with that storage value in-memory AND write `.ordna/config.yaml` with the detected storage key so future runs are stable
  - `{ mode: "ask" }` → throw a new `NeedsModeSelection` error (or similar named export — see Errors below). Caller decides how to prompt.
  - `{ mode: "default-file" }` → load with `storage: file` in-memory; do NOT write a config file (user might `git init` later and re-trigger detection)
- [x] Auto-written `.ordna/config.yaml` contains only the keys needed (storage + tasksDir if relevant); other config keys stay at their schema defaults

### Errors

- [x] New exported error class: `NeedsModeSelection extends Error` with fields `{ cwd: string; reason: string }`. The TUI / web catch this and prompt; the CLI catches it and decides based on TTY.

## Notes

### Why write the config file on auto-detect

Two reasons:

1. **Stability across runs.** Without writing, every invocation would re-run detection (cheap but not free). After one detection, subsequent runs read the config directly.
2. **Explicit > implicit when it matters.** If a teammate clones the repo and sees `.ordna/config.yaml` with `storage: hybrid`, they understand the mode at a glance. Pure auto-detection from refs/files is invisible to readers.

The `default-file` case deliberately does NOT write because:
- The user might be in a non-git scratch directory; auto-creating `.ordna/config.yaml` would litter
- The user might `git init` later — re-detection should re-evaluate from scratch

### Why the env var

`ORDNA_STORAGE=file` (or the others) gives scripted environments a clean way to skip prompts and detection. Useful for:
- CI: never wants a TTY prompt; never wants detection to write files
- New machine setup scripts: explicitly choose the mode without interactive confirmation
- Testing: pin the mode regardless of the test directory's state

Document this in `packages/core/README.md` alongside the `storage:` config key.

### The "ask" prompt UX

Keep it terse. Three options, two-line description each, default `file`. Don't lecture about trade-offs in the prompt — link to the README or core's "Storage modes" section. Users who want a deep dive can read; users who just want to start working should be able to press Enter and get the sensible default.

### Out of scope for T-033

- Migration between modes (file → hybrid → namespace). The detection logic handles "what mode is this?" but not "how do I move from X to Y?" — migration is a separate task. For v1, users wanting to switch modes do it manually: copy the data, change the config, verify.
- Mode-aware help text on every CLI command. The setup page in the web and the TUI modal are the primary touchpoints; other commands just fail fast with helpful errors if they hit a mode mismatch.
- Multi-mode in one repo (e.g., file for some tasks, namespace for others). Not supported. The config picks one mode per project.

### Open question

The `NeedsModeSelection` error is the cleanest contract between core and the consumers (TUI, web, CLI). The alternative — passing a callback into `createContext` — would couple core to specific UI logic. Confirm the error-based contract is the right call before implementing if this gets revisited.

## Progress

- 2026-06-09: Started. Decisions confirmed with user:
  - **`loadConfig` + `createContext` stay sync.** Detection is a separate async function (`detectStorageMode`). Spec said loadConfig would call detection inline, but that forces async ripple through createContext (and the IDE that embeds core). Instead, callers (CLI / TUI / Web wrappers) run an async helper (`ensureStorageConfig`) BEFORE constructing the context — if detection succeeds confidently, it writes `.ordna/config.yaml` and returns; if it lands on `ask`, it throws `NeedsModeSelection` for the consumer to prompt.
  - **`ORDNA_STORAGE` is a runtime override only** — never writes the config file. CI gets predictable behaviour with no on-disk side effects. Users who want stable config use `ordna init --storage=X`.
  - **Detection helper architecture**: `detectStorageMode` (pure, async, returns DetectedMode) → `ensureStorageConfig` (orchestrates: env var override → existing config short-circuit → detection → write or throw) → callers wrap in their own UI flow.
  - **Web setup-page UX**: server starts even on `NeedsModeSelection`; every request returns a barebones HTML setup form until POST `/api/setup-mode` writes the config. After POST the server tells the user to restart (`ordna web` again); in-place transition is more complex than worth in v1.
