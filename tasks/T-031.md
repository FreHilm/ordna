## Goal

Add a second storage mode, `storage: hybrid`, that keeps tasks as markdown files in `tasks/` but moves shared metadata into a single git ref. The blob at `refs/ordna/state` holds `{ next_id, ops }` — a CAS-protected allocator that prevents two offline collaborators from both picking `T-007`, plus an append-only audit log of operations.

After this lands, switching a project from file mode to hybrid mode is one config line:

```yaml
# .ordna/config.yaml
storage: hybrid
```

Working-tree experience is unchanged (tasks are still in `tasks/*.md`). What changes: ID allocation goes through CAS on a git ref, every mutation appends an op to the audit log, and best-effort auto-push keeps the ref in sync with `origin`.

- [x] `packages/core/src/storage/sync-ref.ts` exports a `SyncRef` class:
  ```ts
  interface SyncState {
    next_id: number;     // 1-based; allocate returns formatted id and bumps to N+1
    ops: Op[];           // append-only
  }
  interface Op {
    ts: string;          // ISO-8601 UTC
    actor: string;       // git config user.email with env-var fallback (ORDNA_ACTOR)
    op: "create" | "update" | "move" | "archive" | "delete";
    id: string;
    // op-specific fields TBD in a follow-up (see Out-of-scope)
  }
  class SyncRef {
    constructor(git: GitRunner, refname: string /* default: refs/ordna/state */);
    read(): Promise<SyncState>;                          // empty state if ref missing
    invalidate(): void;                                  // clears in-memory cache
    allocateNextId(config: OrdnaConfig): Promise<string>; // CAS-bump, fetch-and-retry on conflict
    appendOp(op: Op): Promise<void>;                     // CAS-append, fetch-and-retry on conflict
  }
  ```
- [x] `packages/core/src/storage/auto-push.ts` exports a `PushQueue` class:
  ```ts
  class PushQueue {
    constructor(git: GitRunner, refspec: string);
    schedule(): void;          // best-effort, coalesces rapid pushes (~50ms debounce)
    flush(): Promise<void>;    // await any in-flight push; called on dispose()
  }
  ```

### Behavior

- [x] `HybridBackend.init()`: `ensureRepository` + `ensureTasksDir` + lazy-construct `SyncRef` and `PushQueue`
- [x] `HybridBackend.create()`: `sync.allocateNextId` → `writeTaskBytes` → `sync.appendOp({op: "create", id, ...})` → `pushQueue.schedule()`
- [x] `HybridBackend.update()` / `delete()`: same shape — write file, append op, schedule push
- [x] `HybridBackend.list()` / `get()`: read from `tasks/*.md` only (no sync-ref involvement for reads in v1)
- [x] `HybridBackend.watch()`: chokidar on `tasksDir` (same as file mode — sync ref does not drive watcher events in v1)
- [x] `HybridBackend.commit(message?)`: `git add <tasksDir>` + `git commit -m <message>` (same as today). The sync ref is independent of branch commits — only auto-pushed, not auto-committed.

### CAS + auto-fetch on conflict

- [x] When `updateRef` rejects with non-fast-forward, `SyncRef` calls `git.fetchRef(refname)` and retries the read+write once. If the second attempt also fails, surface a clear "sync ref diverged; pull and retry" error.
- [x] No periodic background fetch in v1. Reads use the cached `SyncState`. Writes use the cache + CAS — if the cache is stale, the CAS fails and the fetch-and-retry path picks up the latest state.

### Auto-push

- [x] `PushQueue.schedule()` is fire-and-forget. Multiple calls within ~50ms coalesce to one `git push`.
- [x] Errors logged to stderr (`[ordna-hybrid] push failed: <message>`), never thrown. The user's command stays successful even if the push silently failed.
- [x] `PushQueue` checks `hasRemote()` once at construction. If no `origin` exists, all `schedule()` calls are no-ops. (Implementation note: the check happens lazily on first push, not in the constructor, since `hasRemote` is async and the constructor stays sync. Cached after the first check — identical observable behaviour.)
- [x] `flush()` is called from `dispose()` so a pending coalesced push completes before the process exits.

## Notes

### Sync ref name

`refs/ordna/state` for v1. Single ref, single JSON blob. Easy to extend later (additional namespaced refs like `refs/ordna/locks/<id>` could come later without colliding).

### Op shape — what's stored per op

The minimum required fields (`ts`, `actor`, `op`, `id`) ship in T-031. Op-specific fields (`from`/`to` for `move`, `fields` for `update`, etc.) are flagged as **deferred to a follow-up task** — Fredrik said earlier "let's focus on the functions now," so the op format gets nailed down once T-031's wiring is real and the audit log has concrete usage.

The follow-up task can extend the Op type without breaking T-031's writers; existing entries just have fewer fields than newer ones, which is fine because the consumer (the eventual audit-log viewer) treats them as optional.

### Sync UX recap

Auto-push opportunistically (Fredrik's decision). Every mutation fires a coalesced push. Offline → soft fail; user keeps working. Online → ref stays in sync. CAS handles concurrent writers from different machines; fetch-on-conflict picks up the latest state and retries.

### Out of scope for T-031

- Op-specific fields (move's `from`/`to`, update's changed-field list) — separate refinement task
- Audit-log compaction (snapshot+truncate) — deferred; let the blob grow until it becomes a real issue
- Reading the audit log from the CLI (`ordna log` etc.) — separate task; T-031 only writes
- Watcher integration with the sync ref — v1 keeps the file-watcher pattern; future enhancement could subscribe to ref changes
- Namespace mode (T-032)
- Auto-detect mode (T-033)

### Risk: the shared `git-ref.ts` module also gets used by T-032

T-031 introduces `storage/git-ref.ts`. T-032 (namespace mode) will use the same module. If T-031 and T-032 happen in parallel, coordinate on the GitRunner API surface — T-032 might want methods T-031 doesn't (e.g., `forEachRef` with custom format strings). Add additively in whichever task lands second.

- 2026-06-09: Started. Decisions (reasonable defaults, no clarification needed):
  - **Op classification in v1**: `create()` → `"create"`, `delete()` → `"delete"`, `update()` with `patch.status === "archived"` → `"archive"`, all other updates → `"update"`. `"move"` stays unused in v1; the follow-up that adds op-specific fields (from/to, changed-fields) can refine `update()` to distinguish status-change moves from other updates.
  - **Validation placement**: `storage: hybrid` requires a git repo, and `storage: hybrid` + `schema: backlog` is invalid. Both checks live in `createContext` (after `loadConfig` returns) rather than inside `loadConfig` — keeps `loadConfig` purely about YAML parsing without filesystem awareness beyond reading the config file.
  - **Watcher**: duplicate the file backend's chokidar setup in `HybridBackend` rather than extract a shared helper now. The duplication is ~25 lines; T-032's namespace mode doesn't use chokidar on the tasks dir at all (it polls git refs), so there's no third caller to motivate the extraction yet.
  - **Actor resolution**: `git config user.email` first, then `ORDNA_ACTOR` env var as fallback, then `"unknown"`. Matches the spec's "git config user.email with env-var fallback" wording.
  - **PushQueue debounce**: 50ms trailing-edge — each `schedule()` resets the timer. Burst operations (e.g. `for i in 1..100; ordna create $i`) get coalesced into one push at the end; single-task user actions still get a push 50ms later (one push per action), which is the right trade-off (user gets durability fast; agents/scripts don't spam the network).
