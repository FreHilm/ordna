## Goal

Add an optional sync layer to `FileTaskProvider` that uses a single git ref (`refs/ordna/sync`) as a structured side-channel for two things files are bad at:

1. **Atomic, cross-machine ID allocation** — eliminates "Alice and Bob both created T-007 offline" collisions.
2. **Operation-level audit log** — captures status transitions, assignments, and external-sync events (e.g. Jira pushes) at finer granularity than `git log` over `tasks/*.md` provides.

Tasks themselves stay as plain markdown files. This is a sidecar inside `FileTaskProvider`, not a new provider — the file-first ergonomics (agent direct-edit, `git blame`, Backlog.md compatibility) remain untouched. Activated by one config line:

```yaml
# .ordna/config.yaml
provider: file
sync: ref     # was: none (default)
```

## Acceptance Criteria

- [ ] `OrdnaConfig` (Zod schema in `packages/core/src/config.ts`) gains `sync: z.enum(["none", "ref"]).default("none")`
- [ ] `FileTaskProvider` reads `config.sync` at construction; when `"ref"`, every mutation goes through the sync layer
- [ ] Sync ref location: `refs/ordna/sync` — a single ref pointing at the latest entry in an append-only chain of small JSON blobs
- [ ] Each entry is a JSON blob with: `parent` (OID of previous entry, or `null` for the first), `op` (`"create" | "move" | "update" | "archive" | "delete" | "external-sync"`), `id` (task ID), `ts` (ISO 8601), `actor` (resolved from `git config user.email` with sensible fallbacks), `next_id` (running high-water mark, only on `create`), plus op-specific fields (`from`/`to` for moves, `target`/`externalId` for external-sync, etc.)
- [ ] ID allocation in `FileTaskProvider.create()` uses `max(existing-files-scan, sync.next_id)` — both sources honored, so manually-created files (`touch tasks/T-008.md`) still bump the counter, and sync state is authoritative when present
- [ ] Ref updates use `git update-ref <ref> <new-oid> <expected-old-oid>` for compare-and-swap; on CAS failure (someone else just appended), the provider re-reads the ref, re-derives `next_id`, and retries — bounded retry count (3) with a clear error if it keeps failing
- [ ] If the `git` binary is unavailable, the provider logs one warning and continues with the existing directory-scan ID allocation; sync log entries are silently dropped. No fatal errors.
- [ ] Bootstrap: missing `refs/ordna/sync` is treated as an empty chain. First write creates the ref. Idempotent — adding `sync: ref` to an existing repo Just Works without a migration step.
- [ ] New CLI command `ordna sync` that runs `git push origin +refs/ordna/sync:refs/ordna/sync` and `git fetch origin +refs/ordna/sync:refs/ordna/sync`. Configurable remote via `--remote=<name>` (defaults to `origin`).
- [ ] New CLI subcommand `ordna sync log` that prints the audit chain newest-first, with `--id <task>` to filter to a single task and `--limit <n>` to cap output. Output is human-readable by default, `--json` for machine-readable.
- [ ] Push refused (non-fast-forward) → clear error message: "remote sync log has diverged. Run `ordna sync` to fetch + merge before pushing." (v1 doesn't auto-resolve; user pulls and retries.)
- [ ] Backward compatibility: `sync: none` (the default) preserves existing behavior bit-for-bit. No new code paths run unless explicitly enabled.
- [ ] Concurrency test: two simulated writers in the same process race on `create()` — both succeed, get distinct IDs, sync log has two distinct entries, no duplicate IDs.
- [ ] Smoke test: round-trip — repo A creates T-001 → `ordna sync` → repo B fetches → repo B creates T-002 (not T-001) → both sync logs converge after a final fetch.

## Notes

**Why ship `ordna sync` rather than auto-pushing on every mutation:** [decision: option A]

The decision: ship `ordna sync` as a thin wrapper users invoke explicitly, rather than having `ordna create` opportunistically push the sync ref behind the scenes. Reasons:

- *Predictability beats magic.* A `create` command that sometimes does network I/O is harder to reason about, slower in offline environments, and surprises users when their corp proxy intercepts git over HTTPS.
- *Honest about what's happening.* `git` itself doesn't auto-push branches; users learn `git push` once and apply that mental model everywhere. `ordna sync` is the same shape.
- *Composable with CI / pre-commit hooks.* A user who wants auto-push can add `ordna sync` to a pre-push hook in three lines. A user who doesn't want auto-push can't easily turn it off if it's baked in.
- *Defers the failure-mode question.* If `ordna create` were to auto-push and the remote was unreachable, what happens? Block? Warn? Silent fallback? `ordna sync` makes the failure mode explicit: it either succeeds or the user sees an error and decides what to do.

**Sketch of the entry format:**

```json
{
  "parent": "8a3f2b1c9e7d4f6a8b2e1c3d4f5a6b7c8d9e0f1a",
  "op": "move",
  "id": "T-007",
  "ts": "2026-05-09T10:14:23.451Z",
  "actor": "fredrik@helo.se",
  "from": "doing",
  "to": "done"
}
```

`create` entries additionally carry `next_id` (the allocator high-water mark after this op). `external-sync` entries carry `target` (`"jira"` / `"linear"`) and `externalId` (`"PROJ-123"`). The shape is open-ended — providers and plugins can record their own op types as long as they include the four required fields (`parent`, `op`, `id`, `ts`).

**What this is NOT:**

- Not a CRDT. Concurrent edits to the same task from different machines still rely on git's normal merge for the markdown file content. The sync log is for *allocation* and *audit*, not content reconciliation.
- Not an operation log à la git-bug. git-bug uses op-replay to *reconstruct* state; here, the markdown files are state. The log is purely a side-record.
- Not a replacement for `git log`. `git log -- tasks/T-005.md` still works and remains the source of truth for content history. The sync log captures the dimensions git history doesn't: cross-task operations, status transitions tracked separately from commits, and side-effects (Jira sync, agent runs) that don't produce file changes.

**Conflict scenario (the realistic case):**

Alice and Bob both work offline for a day. Both run `ordna create "Fix the thing"`. Both end up with `tasks/T-007.md` locally and a sync ref where the last `create` op assigned T-007.

Alice pushes first. Her `refs/ordna/sync` is now on the remote.

Bob tries `ordna sync`. The push fails non-fast-forward. He sees:
> remote sync log has diverged. Run `ordna sync` to fetch + merge before pushing.

He runs `ordna sync` again, which fetches Alice's ref. Now Bob has two divergent chains. The v1 behavior: refuse to merge, print both diverging entries, and tell him to renumber his local T-007 (rename the file, update the frontmatter, run `ordna sync` again).

A future T-027 could automate the renumbering — read both chains, find the divergence point, renumber the local task to the next available ID, append a `renumber` op, push. But for v1, manual renumbering is the right tradeoff: it's rare, it's recoverable, and automatic renumbering has subtle correctness traps around in-flight references (`depends_on`, links in PRs, etc.).

**Audit log growth:**

Append-only chains grow linearly. At ~150 bytes per entry and 3 ops per task, 10k tasks costs ~4.5MB. Not a real problem in practice. A periodic snapshot+truncate is nice to have but not a v1 requirement; defer to a later task if/when it becomes a felt issue.

**Implementation placement:**

Sync logic lives entirely inside `packages/core/src/providers/file.ts` as a private helper module (e.g. `packages/core/src/providers/file-sync.ts`) used only when `config.sync === "ref"`. The `TaskProvider` interface is *not* extended — sync is a property of how `FileTaskProvider` chooses to implement the existing methods. Jira and Linear providers don't need it (they have their own audit trails) and don't see this code path.

The CLI commands (`ordna sync`, `ordna sync log`) live in `packages/cli/src/commands/sync.ts` and shell out via the same `git` binary the file provider uses.
