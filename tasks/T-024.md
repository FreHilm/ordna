## Goal

Write the user-facing and plugin-author documentation for the new plugin architecture, then exercise the whole loader path end-to-end so we know it actually works before shipping. **No release in scope** — version bump, changeset, tag, and publish all live in T-030. This task is the verification gate the user clears before authorising the release.

## Acceptance Criteria

### Documentation

- [ ] Root `README.md` gains a "Backends" section under "Packages" explaining the `provider:` config key, with a short table linking to plugin packages once they exist
- [ ] `packages/core/README.md` documents the `TaskProvider` interface and the `createProvider` factory contract that plugin packages must export
- [ ] `packages/core/README.md` adds a "Writing a provider" guide: minimum working example, lifecycle (`init`/`dispose`), `commit` semantics (file-only), error conventions (clear messages, no silent fallbacks)
- [ ] `packages/cli/templates/AGENTS.md` (the AI skill) mentions the existence of plugins and the `provider:` config key — agents need to know the backend is swappable
- [ ] `packages/core/README.md` documents the `loadProvider` error shapes (`Provider "<name>" not installed` and the malformed-package contract error) so plugin authors know what to expect

### Verification

- [ ] Manual smoke test against the existing `tasks/` directory in this repo confirms zero regression in `FileTaskProvider` mode — every CLI command (`create`, `list`, `show`, `move`, `assign`, `commit`, `web`, `board`) behaves identically to `0.1.3`
- [ ] A throwaway in-memory mock provider published locally to a tmp `node_modules/@frehilm/ordna-mock` is loaded successfully via `provider: mock` in `.ordna/config.yaml` — proves the dynamic-import path works for a real external module, not just for the malformed-fixture loader test
- [ ] The mock provider supports a basic round-trip: `ordna create`, `ordna list`, `ordna show <id>`, `ordna move <id> done` — all execute through the loader and the dynamic import path
- [ ] `provider.init?.()` is invoked exactly once when the mock provider is loaded (verified by a console.log marker in the mock)
- [ ] `provider.dispose?.()` is invoked on `ordna web` shutdown and on TUI exit (same marker check)
- [ ] `pnpm -r typecheck` and `pnpm -r build` green
- [ ] `pnpm -r test` green; T-022's loader tests still pass
- [ ] User has personally tested the mock-provider flow on their machine and signed off in this task's Progress section

### Out of scope

- No version bumps. No changeset markdown. No tag. No publish.
- No production plugins (`@frehilm/ordna-jira` is T-008, `@frehilm/ordna-linear` is T-009). The mock provider exists only to prove the loader works; it is not shipped.

## Notes

The mock provider is the closest thing to integration testing the loader without committing to a real plugin. Keep it tiny — maybe 40 lines: an in-memory `Map<string, Task>` with the seven `TaskProvider` methods stubbed and a console.log line at the top of `init` / `dispose`. Put it under `examples/mock-provider/` or `packages/mock-provider/` (not published) so the test recipe is reproducible.

When `@frehilm/ordna-jira` (T-008) ships later, this task's "Backends" section in the root README should grow a row. That work is owned by the Jira plugin task, not this one.
