## Goal

**Umbrella task.** Refactor `@frehilm/ordna-core` so the storage layer becomes pluggable. After this lands, third-party plugins like `@frehilm/ordna-jira` and `@frehilm/ordna-linear` can implement the same interface so the TUI / Web work unchanged against any backend.

The actual work is broken into the granular sub-tasks below. This task closes when all of T-020 → T-024 close.

The end-state for users:

```yaml
# .ordna/config.yaml
provider: jira              # default = file
jira:
  baseUrl: https://acme.atlassian.net
  email: ...
  apiTokenEnv: JIRA_TOKEN
  projectKey: ENG
  jql: "sprint in openSprints()"
```

Same TUI, same Web kanban, different source of tasks.

## Notes

### Architecture

```
@frehilm/ordna-core           defines TaskProvider interface
  ↳ FileTaskProvider          built-in default — markdown files in tasks/
@frehilm/ordna-jira           ← implements TaskProvider (separate package)
@frehilm/ordna-linear         ← implements TaskProvider (separate package)

@frehilm/ordna-cli + ordna-web    consume TaskProvider, agnostic to backend
```

### Schema mismatch (lossy)

Remote trackers carry concepts Ordna doesn't — surfaced as read-only `Task.remote.extras` chips in the UI rather than modeled in core:

| Concept                | Ordna    | Jira / Linear              |
|------------------------|----------|----------------------------|
| Multi-assignee         | no       | yes                        |
| Custom statuses        | yes      | yes (workflows)            |
| Sprints / cycles       | no       | yes                        |
| Epics / parent links   | no       | yes                        |
| Comments               | no       | yes                        |
| Custom fields          | `extra_frontmatter` | many, structured |
| Estimation / story pts | no       | yes                        |
| Reporter ≠ assignee    | no       | yes                        |

### Open decisions (chosen defaults — adjust per task as needed)

- **`createContext` becomes async.** OK to break — this is a 0.2.0.
- **Auto-install vs explicit install of plugins.** Explicit. Throw with the install command on missing plugin.
- **One provider per repo, or multiple boards?** v1 = one. Multi-board deferred.
- **Status name handling.** Provider supplies the live status list dynamically (`provider.statuses?: () => Promise<string[]>`); core uses it instead of `config.statuses` when present. Keeps Jira / Linear native column names.
- **Read-only or read-write in v1?** Read-only first per backend (faster path to user value), write follows in a `0.x` minor.
- **`depends_on` enforcement on remote backends.** Stays a client-side gate in core. Remote workflow rules are an additional layer; both errors surface to the user.

### Ordering

Strict for Phase 1: T-020 → T-021 → T-022 → T-023 → T-024 (each builds on the previous).
After Phase 1: T-008 (Jira) is the next critical-path task. T-009 (Linear) follows T-008 to reuse mapping helpers.
